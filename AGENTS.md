# Cakeopedia shared working instructions

Existing Austin home-baking business; first website. Repo: immazhark/cakeopedia-website.

## Start
Also read docs/directives/MASTER-DESIGN-ENGINEERING-DIRECTIVE.md (permanent owner directive) and DESIGN.md every session; track status in docs/qa/DESIGN-IMPLEMENTATION.md.
Read the current task, docs/shared-context-and-decisions.md, docs/handoff.md and docs/progress.md; inspect branch/HEAD,
working changes and relevant PRs. Read docs/master-plan.md and task specifications
only as needed. Repository code is implementation evidence; plans are not.

## Scope and cost
Follow the active task's authority. Read-only means no repository or provider writes.
Use suitable commercially permitted free services. No purchases, trials with billing,
paid APIs, deployment, account provisioning or public launch without matching authority.
Check actual account plans/quotas before calling a service free. Alerts are not caps.

## Facts and privacy
Publish only owner-approved facts and genuine permission-cleared work. Previous work
is not a current menu product. Do not invent prices, reviews, health/allergen promises,
service areas or finished-product/kitchen certification. Hyderabad is origin, Austin
is current context. Keep customer data, home address, private owner responses, original
media, secrets and exports out of Git/public CMS/logs/analytics.

## Product and engineering
Static-first public pages; small typed APIs. Server validation and authorisation on
every private route. Durable enquiry and outbox before success; test replay, storage,
notification and auth failure. No checkout/customer accounts by default. Owner-approved optional inspiration uploads (up to three images) require private storage and release-critical validation/auth/abuse/deletion proof before activation.
Keep public editorial content separate from private operations. No fabricated cakes,
forced intros, scroll hijacking or essential hover/motion; keyboard and reduced-motion
users retain full functionality.

## Collaboration and proof
One primary writer per task; isolated branches/worktrees for authorised concurrency.
Coordinate dependencies, schemas, migrations and shared design files. Preserve others'
changes. Use focused meaningful tests; report actual commands/results and limitations.
Do not describe mocks as cloud verification, a build as visual proof, or lab scores as
field data. Block release-critical failures; continue independent work when blocked.
Use relevant existing tools selectively, not bulk skill installations.

## Handoff
Update only materially affected decisions/specs. Record task, branch/HEAD, changed
paths, actual checks, unresolved holds, provider changes and the next precise action
in docs/handoff.md; merged status in docs/progress.md. Never import whole chat histories
or repeatedly regenerate the programme. Instructions do not create technical permissions.
