# Acceptance checklist

## Product and integrity
Approved names/menu/policies; no fabricated claims; previous work distinct from current products; image rights established; no location metadata; no screenshot crops masquerading as final originals. Hyderabad origin/public story approved before publication.

## Customer and owner
Browse and back-navigation work; creation reference reaches enquiry; optional/unsure inputs accepted; successful durable submission acknowledged; retry safe; form failure truthful. Owner can publish a prepared creation, inspect/reply to an enquiry and change availability on her phone; observe rather than assume.

## Accessibility and visual quality
Keyboard/focus/dialog checks; readable enlarged text; reduced motion; meaningful alt text; no critical information behind hover. Review real mobile/desktop renders against selected target. Automated scans do not prove WCAG conformance.

## Reliability/security
Persistence and outbox atomic; duplicate submit; DB failure; notifications fail/retry; quota exhaustion; unauthorised access; upload failure if enabled; no personal logs/caches; backup/export and restore test. No customer data in git/CMS public dataset.

## Performance/cost
Static routes stay cheap; measured API CPU; responsive images; no unnecessary runtime transformations; constrained-device lab checks. Field LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 at p75 only evaluated when sufficient real data exists. Account limits/licences/overages recorded; no unauthorised expenses.

## Launch
Owner content/workflow review complete; domain selected; actual fulfilment/contact claims verified; staging data separate; maintainer/recovery documented; explicit public-release instruction obtained when needed under current user authorisation. No payment release until its business/legal requirements are confirmed.
